Mettre à jour le firmware vers ArduPlane 4.7.2 (en gardant vos paramètres)

Objectif : remplacer ArduPlane 4.7.1 par la dernière version stable 4.7.2, avec la bonne version pour votre carte (Pixhawk1), sans perdre l'ancienne configuration du Y3. Ensuite, vérifier que les paramètres ont été conservés.

État actuel (20:39) : toujours sous ArduPlane 4.7.2 (fb773567), confirmé à chaque démarrage. Le PreArm « Radio failsafe on » mentionné ici a été corrigé au Guide 04 (l'encodeur PPM nécessite le mode de sortie i6X PWM). Remarque : juste après la connexion, il peut manquer environ 144 réglages VTOL (Q_…) dans la liste des paramètres de QGC. Utilisez toujours Parameters → Tools → Refresh environ 30 s après le démarrage avant d'enregistrer une sauvegarde (constaté à 20:11).
Sécurité pour ce guide
  • USB uniquement. Pas de LiPo. La documentation de QGC indique que l'appareil ne doit pas être alimenté par batterie pendant le flashage.
  • Gardez votre Mac branché sur son chargeur. Ne débranchez jamais le câble USB pendant que la barre de progression avance.
  • Si quelque chose tourne mal, le Pixhawk n'est pas « briqué » : son bootloader reste sur la carte et vous pouvez toujours le reflasher.

  • Carte : Pixhawk 2.4.8, cible ArduPilot Pixhawk1 (version complète 2 Mo) · sous ArduPlane 4.7.1 · QGC 5.1.5 sur macOS.
  • Ancienne configuration = configuration Y3 complète (Tri, bascule VectoredYaw, empennage en V…), jamais volée. Décision : la garder et la corriger dans les guides suivants.
  • Sauvegarde : backups/params-backup_2026-10-17_before-guide02.params ✅
  • J'ai vérifié le serveur officiel des firmwares ArduPilot (02:19) : Plane/stable/Pixhawk1/ = "Plane: version to 4.7.2", compilé le 2026-10-13. 4.7.2 est donc bien la version stable actuelle pour votre carte.

Pourquoi les paramètres devraient être conservés

Le firmware (le programme) et les paramètres (vos réglages) sont stockés à des endroits différents. Sur un Pixhawk 1, les paramètres sont dans une puce mémoire séparée (FRAM). Une mise à jour normale ArduPlane → ArduPlane ne remplace que le programme. ArduPilot convertit automatiquement les paramètres renommés. Les paramètres ne sont effacés que si vous installez un autre type de véhicule (par ex. Copter). C'est pourquoi l'étape 4 comporte une liste de contrôle : il faut que ce soit Plane.

Certains utilisateurs ont quand même constaté des réinitialisations (rare), c'est pourquoi nous avons fait la sauvegarde et pourquoi l'étape 7 vérifie.

5b

« Vehicle did not return the full parameter list » : se reconnecter proprement

Vu à 02:38, juste après le redémarrage. Cela ne veut pas dire que vos paramètres sont perdus. QGC s'est reconnecté alors que la carte était encore en train de démarrer (voir « Beginning INS calibration… ») et a commencé à télécharger tous les paramètres avant que la carte soit prête, donc le téléchargement était incomplet. Au premier démarrage d'un nouveau firmware, ArduPilot peut aussi être en train de convertir des paramètres, ce qui prend plus de temps.

  1. Débranchez l'USB, attendez 5 secondes, rebranchez-le.
  2. Ne touchez pas la carte et ne cliquez sur rien pendant 30 secondes (calibration des gyroscopes au démarrage + téléchargement des paramètres). Surveillez la barre de progression sous la barre d'outils supérieure de QGC.
  3. Ouvrez à nouveau Vehicle Configuration. Les pages devraient maintenant s'ouvrir normalement.

Toujours le même message ? Dans Parameters → Tools, cliquez sur Refresh. Toujours en échec → faites une capture et envoyez-la-moi ; ne chargez pas encore la sauvegarde.

Solution de repli : installer depuis un fichier téléchargé

À utiliser uniquement si les étapes 2–3 ne fonctionnent pas (carte jamais détectée, ou Plane/Pixhawk1 non proposé) :

  1. Téléchargez le fichier officiel : firmware.ardupilot.org/Plane/stable/Pixhawk1/arduplane.apj. Utilisez le fichier .apj, pas le .hex (documentation ArduPilot : le .hex sert uniquement en DFU/JTAG).
  2. Page Firmware → Flash → débrancher/rebrancher → dans la fenêtre Firmware Setup : ArduPilot → cochez Advanced settings → dans la liste des versions, choisissez "Custom firmware file…" → OK → sélectionnez le fichier arduplane.apj téléchargé.
  3. Puis reprenez à l'étape 5.

⚠️ Un nouveau message : PreArm: Internal errors 0x100000 l:1375 flow_of_ctrl

Il est apparu une fois au démarrage (02:44:24 Critical: Internal Errors 0x100000). Il n'était pas dans le journal de démarrage de la 4.7.1. Je l'ai décodé à partir du code source d'ArduPilot 4.7.2 :

  • 0x100000 = contrôle interne "flow_of_control" (situations « on ne devrait jamais arriver ici »).
  • l:1375 = ligne 1375 de AP_HAL_ChibiOS/RCOutput.cpp, dans RCOutput::push() : les sorties servos/moteurs ont été envoyées (« push ») sans avoir d'abord été regroupées (« cork »). C'est un contrôle logiciel de séquencement sur le pilote des sorties, pas un capteur cassé ni une carte défectueuse.
  • Le code de Plane qui pilote les sorties n'a pas changé entre 4.7.1 et 4.7.2 (j'ai comparé les deux versions). Le déclencheur est donc plus probablement la configuration que la mise à jour. Une piste est le SERVO7_FUNCTION = 39 nouvellement affecté automatiquement sur un Tri VectoredYaw, mais c'est une hypothèse, pas une certitude.
  • Il empêche l'armement (c'est une erreur PreArm), il doit donc avoir disparu avant tout test moteur. Il n'a pas d'importance pour les guides suivants (orientation, calibration).
8

Test de suivi : l'erreur interne revient-elle ?

Les erreurs internes sont mémorisées jusqu'au prochain redémarrage, nous vérifions donc si elle se reproduit lors d'un démarrage propre :

  1. Débranchez l'USB, attendez 5 s, rebranchez-le. Ne touchez pas la carte pendant 30 s.
  2. Ouvrez Vehicle Messages et cherchez Internal Errors.
Compte rendu : « L'erreur interne est revenue » ou « disparue ». Copiez-collez les messages comme la dernière fois.

Selon la réponse, soit je poursuis l'investigation (un changement de paramètre à la fois, expliqué au préalable), soit nous passons au Guide 03. Ne modifiez encore aucun paramètre vous-même pour cela.
