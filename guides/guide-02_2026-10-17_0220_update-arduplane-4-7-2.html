Why the parameters should survive

The firmware (the program) and the parameters (your settings) are stored in different places. On a Pixhawk 1, the parameters live in a separate memory chip (FRAM). A normal update from ArduPlane → ArduPlane only replaces the program. ArduPilot converts any renamed parameters automatically. Parameters are wiped only if you install a different vehicle type (e.g. Copter). That's why step 4 has a checklist: it must say Plane.

Some users have seen resets anyway (rare), which is why we made the backup and why step 7 checks.

⚠️ One new message: PreArm: Internal errors 0x100000 l:1375 flow_of_ctrl

This appeared once at boot (02:44:24 Critical: Internal Errors 0x100000). It was not in the 4.7.1 boot log. I decoded it from the ArduPilot 4.7.2 source code:

  • 0x100000 = internal check "flow_of_control" ("should never get here" situations).
  • l:1375 = line 1375 of AP_HAL_ChibiOS/RCOutput.cpp, in RCOutput::push(): the servo/motor outputs were sent ("push") without first being grouped ("cork"). That's a software timing check on the output driver, not a broken sensor or bad board.
  • The Plane code that drives outputs didn't change between 4.7.1 and 4.7.2 (I compared the two versions). So the trigger is more likely the configuration than the update. One candidate is the newly auto-assigned SERVO7_FUNCTION = 39 on a VectoredYaw Tri, but that's a hypothesis, not proven.
  • It blocks arming (it's a PreArm error), so it must be gone before any motor test. It doesn't matter for the next guides (orientation, calibration).
